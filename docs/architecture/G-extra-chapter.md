# G. 購入(本編の解放・追加の章)と追加の章の作り

状態: 設計。本編の解放(§1.4)は M-01 で作る。追加の章は本編がそろってから。オーナーの決定「物語の続きを有料の追加の章で出す」「広告をやめる」「最初の部分を無料にし、本編の残りを 1 回の購入で解放する」「どの配信先でもオフラインで遊べる(購入の権利もオフラインで有効)」(いずれも 2026-10-02)に合わせる。追加の章の範囲と中身にかかわる決まりは、非公開の reforge-plan の側にある。
公開リポジトリなので、物語の語も、場面の中身が推し量れる言い方も書かない。呼び名は「本編」と「追加の章」(コードでは `chapter2`)と、節目の ID(`main.mark`・`main.final`)だけにする。

## 1. 買う仕組み(DEC-G1〜G5)
他の配信先: Android は同じ形(最初の部分は無料・1 回の非消耗型の購入で解放・端末の購入の記録でオフライン判定)。Steam は買い切りで、体験版を別に付ける(本体の門は同じ区切りのデータを使える)。追加の章はどの配信先でも有料。この文書の細目は iOS(StoreKit 2)の分。

### 1.1 品
| 品の ID | 種類 | 表の名前(ストアの原稿 `store/iap/<ID>/<地域>.json`。L-14) | 権利 |
|---|---|---|---|
| `reforge.fullgame` | 非消耗型 | 本編の解放 | 区切りから先の本編を遊べる(§1.4) |
| `reforge.chapter2` | 非消耗型 | 追加の章 | 追加の章を遊べる(始めるには `main.final` が要るので、本編の解放が先にある) |

- 値段はオーナーが決める(答え待ち)。アプリは値段を持たず、StoreKit の表示の文字列をそのまま出す(L10n §12.2)。
- `ProductID` に `fullgame`(M-01)と `chapter2`(X-01)を並べる。`store/iap/<品の ID>/` を 5 言語で置く(`check-store-metadata.py` が品ごとの 5 言語を確かめる)。

### 1.2 権利の確かめ(DEC-G2)
- 根拠は StoreKit の取引の記録だけ。StoreKit 2 は取引を Apple の署名付き(JWS)で端末に持ち、`Transaction.currentEntitlements` は通信なしで読める。`VerificationResult` が端末の上で署名を確かめるので、`.verified` で `revocationDate == nil` の取引の品の ID の集まりを権利とする。
- 起動時と、前に出たとき(`scenePhase == .active`)に読み直す。起動中は `Transaction.updates` を待ち受け、来た取引を `finish()` して読み直す(買った・家族共有の追加・払い戻しの取り消しがここで来る)。
- **通信を切っても抜け道にならない**: 権利はアプリが書く印ではなく署名のある取引の記録から作るので、機内にしても、印のファイルを書き換えても、権利は増えない。非消耗型は期限を持たないので、端末の時計を動かしても変わらない。`.unverified` は権利にしない。
- 払い戻し: 取り消しは、端末が次にストアと同期したときに記録に入り、その時点で権利が消える(通信が無い間は、最後に同期した記録のまま)。
- アプリが自分で書く印(`UserDefaults` など)は使わない。表示を早くする覚えが要るなら、それは画面の表示だけに使い、門の判定には使わない。
- **権利を保存(`SaveEnvelope`)には入れない**。保存はどの端末でも同じに読めるものにし、権利は端末と Apple ID の側に置く。

### 1.3 画面
- 追加の章の案内は、タイトルの一覧の 1 行(`main.final` がある人だけ。§4.2)と、設定の購入の所だけに置く。本編の場面とクレジットには、購入・値段・案内を出さない(非公開の側の決まり。テストは §4.1)。
- 「購入を復元」は設定の購入の所に 1 つ(非消耗型の決まり)。本編の解放の案内は、区切りで止まったときの 1 枚と、設定の購入の所だけに置く(§1.4)。

### 1.4 本編の解放(DEC-G5。M-01)
- 区切り: コンテンツの定義 `trialGate`。`when`(条件 1 つ。区切りに着いたか)と、形 `mode`(既定 `fence`)と、待たせる物 `holds`(研究を始めること・挙げた出来事)。位置と待たせる物はデータが決める(game-designer の候補からオーナーが決める。それまでは定義が無く、門は閉じない)。区切りに着く時点(夜明けまで待つ、など)もデータで書く。
- 本体の門: 本体は「権利があるか」を外から受け取る(`Simulation` の環境。保存には入れない)。権利が無く `when` が成り立つ間、
  - `fence`(既定): 時計・手の作業・生産・探索・戦闘は続く。`holds` の物だけが待つ: 研究を始める命令は理由つき(`reason.trial.locked`)で断り、挙げた出来事は起こさずに世界の待ちの列に積む。
  - `freeze`: 世界ごと止める(時計を進めない・命令を断る)。
  - どちらの形も `Frame` に「区切りに着いた」を出し、画面は案内の札を 1 枚出す。
- 権利を得たら(買った・復元した)、同じ世界がそのまま続く(作り直さない)。待ちの列の出来事は、積んだ順に起こす。権利が消えたら(払い戻し)、条件が成り立っている所でまた待つ。
- 待ちの列は世界の状態なので保存に入る。区切りより先の保存を権利の無い端末で読んでも、条件が成り立っていれば同じに待つ。体験版(Steam)の保存は、製品版でそのまま続く。
- 門は世界の条件で決まるので、時計や保存のファイルを動かしても越えられない。
- どちらの形にするかは、オーナーが試遊の後に決める(既定の案: `fence`)。データの `mode` を替えるだけで切り替わる。

## 2. 封をした本文の出し分け(DEC-G6〜G9)
### 2.1 束
| 束 | 中身 | 鍵 |
|---|---|---|
| `private.sealed` / `text-<言語>.sealed` | 本編の非公開の層(L-04 の形) | 本編の鍵 |
| `chapter2.sealed` / `chapter2-text-<言語>.sealed` | 追加の章の層(言語に依らない JSON と、言語ごとの文言) | 追加の章の鍵 |

- 形は今の `RFS1`(合図 + nonce + AES-256-GCM)のまま。束ごとに nonce を変える。
- `rf-seal` に「層の名前」を渡せるようにする(本編 = `private`、追加の章 = `chapter2`)。`stage.sh` が両方を作る。
- CI の確かめに足す: ipa の中に、追加の章の平文の JSON・文言が無い(今の「非公開の絵の指紋が ipa に無い」と同じ作り)。

### 2.2 どこまで守るか
- 守れるもの: ipa を開いて眺める・ファイルを検索する・ストアの外で配られた ipa を覗く、の程度で、本文と答えが見えない(ネタバレの防止)。買っていない人の端末でも、束は開かれず、メモリにも展開されない。
- 守れないもの: アプリの本体を解析して鍵を取り出す人。鍵は、オフラインで開くためにアプリに入っている。これは本編の束と同じ水準で、DRM ではない。
- この水準を選ぶ理由: 完全オフラインの決まりを守ると、鍵をサーバから受け取る形が取れない。強くしたくなったら、そのときに「買った後に鍵をサーバから受け取って端末の Keychain に置く」形へ替えられる(束の形は変えずに、鍵の置き場だけを替える)。**本編の束と同じ水準に決まった**(オーナーの決定 2026-10-02)。

### 2.3 大きさ
- 追加の章の文言は、1 言語あたり 0.5〜1.6 MB の見込み(本編の L10n §6.2 と同じ桁)。5 言語と言語に依らない部分で 3〜9 MB を同梱する。字体(4.7 MB)と同じ桁で、ipa の大きさの心配は小さい。合計が 30 MB を超えたら、後から落とす形(Background Assets)を考え直す。

## 3. 本体の側(DEC-G10・G11)
### 3.1 遊ぶ場ごとの ContentDB
- 今の層の仕組み(公開 → 非公開。後の層が同じ ID を置き換え、`remove` で消す)に、3 つ目の層として追加の章を重ねる。
- 追加の章は、`start`・`mapGen`・`clock` のような 1 つしかない定義を、本編と違う値で持ちうる。本編を遊ぶときに重ねると本編が変わってしまうので、**遊ぶ場(campaign)ごとに ContentDB を作る**:
  - 本編: 公開 → 非公開。
  - 追加の章: 公開 → 非公開 → 追加の章。
- `ContentLoader.loadBundled(root:key:)` に「遊ぶ場」を渡す口を足す(`campaign: .main / .chapter2`)。追加の章の場は、権利があるときだけ作る(DEC-G9)。
- どの場の保存かは、保存の封筒の `content`(遊んでいた層の ID と版。今もある)で分かる。`chapter2` の層を含む保存は、追加の章の場で開く。権利が無い端末でその保存を読もうとしたら、「この記録は追加の章のもの」と出して開かない(保存は消さない)。
- 保存の形(`SaveEnvelope`・`WorldState`)はこのために変えない。

### 3.2 節目の枠
- `SaveSlot` に `case milestone(MilestoneID)` を足す(ファイル名 `milestone-<ID>`)。`MilestoneID` は RFKernel の型付き ID。本編では 2 つ:
  - `main.mark`・`main.final`。どの時点で書くかは非公開のデータが決める。`main.final` は本編を終えた時点。
- 書く時: コンテンツの効果 `Effect.milestone(MilestoneID)` が出た時点で、画面が自動で書く(夜明けの自動セーブと同じ流れ。`SaveBook.writeMilestone`)。同じ ID は上書き(最新が残る)。
- 消さない: 「最初から」でも、ロードでも、巻き戻しでも消さない(手動の枠と同じ扱い)。
- `main.final` があれば、本編を終えた時点に着いたとみなす(タイトルの 1 行。§4.2)。
- 保存の形への影響: `SaveSlot` の case が 1 つ増えるだけで、今の保存はそのまま読める。凍らせた見本も変わらない。アプリの switch(`check-app-switches.py`)は網羅を直す。

### 3.3 追加の章の始め方
- タイトルの「追加の章」(権利あり・`main.final` あり): 節目の枠の世界を読み、追加の章の場の ContentDB で、`ChapterBridge.begin(from:content:)` を当てて新しい世界を作る。遷移できるか・どの枠を読むかは、非公開の進行状態で決める。本体は節目の意味を知らない。
- 遷移のデータの選び方は、非公開の設定(`ChapterBridge` が読むコンテンツの定義)に従う。形は巻き戻しの `MemoryCarry` と同じ(世界状態の集まりごとに「持ち越す / 定義から作る」)。
- どの場合も、本編の保存(自動・手動・中断)はそのまま残す。
- 追加の章の中の保存は、本編と同じ規則(D-save §7)。夜明けの自動・手動・中断。巻き戻しは追加の章の夜明けの中だけ。

## 4. 確かめ
### 4.1 テスト
- 本体: 遊ぶ場ごとの ContentDB(本編の場に追加の章の定義が混ざらない・追加の章の場は上に重なる)。節目の枠の書き方と消えなさ。`ChapterBridge` の遷移の定義。権利の無い場で `chapter2` の層を含む保存を開かない。
- アプリ(macOS の CI): 権利の確かめ(StoreKit のテスト用の設定ファイル `.storekit` で、買う・復元・払い戻し・家族共有)。
- 静的: 本編の場面とクレジットの文言に、購入・値段・追加の章の文言 ID(`ui.store.*`・`ui.chapter2.*`)が無い(非公開の側の TEST-E1)。
- ボット: 本編を終えた時点まで遊び、権利の無いままクレジット・タイトルまで、購入の画面が一度も出ない(非公開の側の TEST-E3)。
- CI: ipa に追加の章の平文が無い。

### 4.2 タイトルの 1 行
- 出す条件: `main.final` がある(本編を終えた時点に着いた)。権利が無ければ「追加の章」の 1 行から設定の購入の所へ。権利があれば始める(§3.3)。`main.final` が無い人には出さない(「本編を終えると始められる」は、設定の購入の所の説明にだけ書く)。
